\section{HITL Collaboration Confirmation Test}
\label{sec:test-hitl}

Objective: validate whether task submission is strictly gated by explicit confirmation and whether credit accounting is consistent with observed runtime behavior.

\subsection{Source-code Logic of HITL}
\label{sec:hitl-code-logic}

The HITL mechanism is implemented in the agent orchestration layer with an explicit state machine:
\texttt{IDLE $\rightarrow$ PENDING\_CONFIRMATION $\rightarrow$ CONFIRMED $\rightarrow$ SUBMITTED}.
At runtime, when a task-like plan is detected in the assistant output, the session enters
\texttt{PENDING\_CONFIRMATION}. In this phase, user input is strictly matched against exact confirmation/rejection keywords
(\texttt{confirm/yes} vs. \texttt{cancel/no}); non-matching inputs are short-circuited and do not proceed to tool execution.

The submit tool is additionally gated at execution time: \texttt{submit\_rshub\_task} is blocked unless the HITL state is
\texttt{CONFIRMED}. After successful submission, credits are deducted through the credit service and the state is marked as
\texttt{SUBMITTED}. Therefore, the current implementation should be validated with two views:
(1) logical workflow expectation (plan-stage + execution-stage accounting), and
(2) observed code behavior (submission-stage deduction after successful execution).

\subsection{A-Test Observations}
Based on the latest A-test run, the following behavior is observed:
\begin{itemize}
	\item \textbf{Confirm path}: submission succeeds when the user provides exact confirmation keywords.
	\item \textbf{Cancel path}: task is not submitted and no credit is deducted.
	\item \textbf{Timeout path}: currently observed as no submission and no credit deduction; however, a full timeout-triggered auto-cancel case has not been reached within the three-day test window.
	\item \textbf{Keyword strictness}: only strict confirm/cancel keywords are accepted; non-matching user inputs do not trigger submission.
	\item \textbf{Credit behavior}: one successful submission currently deducts \textbf{1 credit} in observed runs.
\end{itemize}

\section{Chapter Summary}

This chapter evaluates three implementation-focused improvements and reports their current validation status.
For HITL confirmation, observed behavior is consistent with the enforced safety rule: submission is gated by explicit confirmation, and credits are deducted only on successful submission (1 credit).
For GitHub--PyPI synchronization, the tested scenarios show expected branch-state handling, including fast-forward success, merge-capable divergence handling, and fail-fast conflict reporting with manual confirmation requirements.
For skill architecture optimization, baseline and tiered modes both complete single-turn tasks, while tiered loading shows more stable multi-turn context continuity in repeated tests.

Overall, the implemented changes improve behavioral correctness and operational reliability in the current iteration.
Remaining work is mainly quantitative expansion, including full end-to-end stability statistics and finer-grained token/latency instrumentation.
